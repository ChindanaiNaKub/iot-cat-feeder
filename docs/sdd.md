# SDD เครื่องให้อาหารแมวอัตโนมัติ

สถานะเอกสาร: ฉบับร่าง 0.9 · 30 ตุลาคม 2569
อ้างอิง: `docs/srs.md`

เอกสารนี้อธิบายว่าสร้างระบบอย่างไร ความต้องการอยู่ใน SRS

## 1. ภาพรวม

ระบบเป็นเฟิร์มแวร์ชิ้นเดียวที่รันบน NodeMCU v3 ทำสามอย่างวนซ้ำในลูปเดียว คือ รับคำขอ HTTP ตรวจเวลาตั้งอาหาร และปิดฝาเมื่อครบเวลา ไม่มี task หรือเธรดแยก ไม่มีเซิร์ฟเวอร์ภายนอก

เหตุผลที่เลือกทำบนบอร์ดเองคือ หน้าห้องสอบไม่การันตีอินเทอร์เน็ต ถ้าสาธิตผ่าน cloud ไม่ได้ก็ยังสาธิตผ่าน Wi-Fi ในวงได้

## 3. ฮาร์ดแวร์

### 3.1 การต่อขา

| อุปกรณ์ | ขา NodeMCU | ขา GPIO | หมายเหตุ |
|---|---|---|---|
| Servo สัญญาณ | D5 | 14 | PWM |
| Servo ไฟบวก | VIN | 5V จาก powerbank | ห้ามใช้ 3V3 |
| Servo กราวด์ | GND | GND | ต้องกราวด์ร่วมกับบอร์ด |
| Capacitor 470 µF | คร่อม VIN กับ GND | ไม่มี | ขั้วบวกเข้าฝั่ง VIN |
| LED ทดสอบ | D4 | 2 | ใช้ตอน bring-up เท่านั้น |
| HC-SR04 ตรวจจับแมว | ยังไม่กำหนด | ยังไม่กำหนด | ต้องมีตัวแบ่งแรงดันที่ ECHO |
| HC-SR04 วัดระดับ | ยังไม่กำหนด | ยังไม่กำหนด | ต้องมีตัวแบ่งแรงดันที่ ECHO |

### 3.2 วงจรจ่ายไฟ

```text
powerbank 5V 2A
      │
      ├──────────────> VIN ของ NodeMCU ──> regulator บนบอร์ด ──> 3.3V ให้ชิป
      │
      └──────────────> V+ ของ servo
                          │
                    ┌─────┴─────┐
                    │ 470 µF    │  คร่อมระหว่าง V+ กับ GND
                    └─────┬─────┘
                          │
                         GND ──── ร่วมกับ GND ของ NodeMCU
```

เหตุผลที่ต้องมี capacitor วัดจากการทดลองตอน bring-up คือ เมื่อ servo เริ่มหมุน กระแสกระชากทำให้แรงดันไฟตกชั่วขณะ บอร์ดรีบูตค้าง ไฟล์ `firmware/servo_test/servo_test.ino` ใช้ทดสอบข้อนี้แยกจากโค้ดหลัก การจ่ายไฟจากพอร์ต USB ของโน้ตบุ๊กจ่ายกระแสไม่พอ ต้องใช้ powerbank

การแยกกราวด์ไม่ได้ทำ เพราะ servo และบอร์ดต้องอ้างกราวด์เดียวกันเพื่อให้สัญญาณ PWM มีความหมาย

### 3.3 การคาลิเบรต servo

โค้ดสั่งมุม `OPEN_DEG = 180` แต่ servo ตัวที่ใช้ให้ระยะจริงประมาณ 95 องศาแล้วชนที่จำกัดการหมุนของถัง ค่าที่ใช้จริงจึงถูกจำกัดด้วยกลไก ไม่ใช่ด้วยตัวเลขในโค้ด ถ้าเปลี่ยน servo ต้องวัดระยะจริงใหม่และแก้ `OPEN_DEG`

## 4. เฟิร์มแวร์

### 4.1 โครงสร้างไฟล์

ไฟล์เดียว `firmware/feeder/feeder.ino` แบ่งเป็นห้ากลุ่ม

| กลุ่ม | ฟังก์ชัน | หน้าที่ |
|---|---|---|
| หน้าเว็บ | `PAGE` | HTML และ JavaScript ฝังใน PROGMEM |
| เวลา | `clockText`, `scheduleText`, `checkSchedule` | อ่านเวลาจาก NTP และเทียบกับตารางมื้อ |
| สถานะ | `markFeed`, `struct Feeder` | นับครั้งและจำเวลาล่าสุด |
| งาน actuation | `feed`, `closeFlap` | สั่ง servo และปิดฝา |
| เครือข่าย | `keepWifi`, `statusJson`, handler ทั้งสาม | ต่อ Wi-Fi และให้บริการ HTTP |

การเลือกใช้ฟังก์ชันเดียวแทนคลาส เพราะมีผู้เรียกน้อยและสถานะมีชุดเดียว ไม่ต้องมี abstraction เพิ่ม

### 4.2 ลำดับการเริ่มระบบ

1. เปิด Serial ที่ 115200
2. `servo.attach(D5)` แล้วสั่งปิดฝาทันที เพื่อไม่ให้ฝาค้างจากรอบก่อน
3. เริ่ม Wi-Fi แบบ station
4. ตั้ง `configTime` ขอเวลาจาก `pool.ntp.org` และ `time.nist.gov` ที่ UTC+7
5. ลงทะเบียนเส้นทาง `/`, `/status`, `/feed` และตัวจัดการ 404
6. เริ่ม HTTP server
7. เข้าลูป

NTP เป็นแบบ asynchronous จึงไม่บล็อกตอนบูต ช่วงแรกที่ยังไม่ได้เวลา `clockText()` คืนค่า `--:--:--` และ `checkSchedule()` ไม่ทำงาน เพราะเวลายังน้อยกว่าค่าอ้างอิง 1600000000 วินาที

### 4.3 ลูปหลัก

```text
loop():
  server.handleClient()                     รับ HTTP
  ถ้า feeder.open และเปิดมานานกว่า 900 ms
      closeFlap()                           ปิดฝาบังคับ
  checkSchedule()                           เทียบเวลากับตารางมื้อ
  keepWifi()                                ต่อ Wi-Fi ใหม่ถ้าหลุด
```

ลูปไม่มี `delay()` จึงตอบ HTTP ได้ตลอดเวลา การปิดฝาใช้การเทียบ `millis()` ไม่ใช่ `delay(900)` ข้อนี้สำคัญเพราะถ้าใช้ `delay` หน้าเว็บจะค้างทุกครั้งที่ให้อาหาร

### 4.4 ตารางมื้อและตัวกันซ้ำ

`checkSchedule()` สร้างกุญแจเวลา `key = (วัน * 100 + ชั่วโมง) * 100 + นาที` แล้วเทียบค่ากับ `lastMinuteKey` ถ้าซ้ำให้ออกทันที วิธีนี้ทำให้แม้ลูปจะวิ่งหลายพันรอบต่อนาที ก็ให้อาหารเพียงครั้งเดียวต่อหนึ่งนาที

หลังจับคู่เวลาได้ จะเรียก `feed("ตั้งเวลา")` แล้ว `return` ออกทันที ไม่ตรวจมื้อถัดไปในรอบเดียวกัน

### 4.5 แหล่งที่มาของการให้อาหาร

| แหล่ง | ผู้เรียก | สถานะ |
|---|---|---|
| `เว็บ` | handler ของ `POST /feed` | ใช้งานแล้ว |
| `ตั้งเวลา` | `checkSchedule()` | ใช้งานแล้ว |
| `เซ็นเซอร์` | ตัวตรวจการเข้ามาใกล้ | แผน รอของ |

### 4.6 โมเดลสถานะ

```text
              feed()
   ┌────────┐ ─────────> ┌────────┐
   │ ปิดฝา  │            │ เปิดฝา │
   └────────┘ <───────── └────────┘
        ▲      ครบ 900 ms      │
        │                      │
        └──────────────────────┘
          ปิดฝาบังคับในลูป

สถานะเพิ่มเติมเมื่อเพิ่มเซ็นเซอร์
   IDLE ──แมวเข้าใกล้──> CHECK ──ยืนยัน 3 รอบ──> FEED ──> COOLDOWN 30 นาที ──> IDLE
```

สถานะ `open` เป็น boolean ตัวเดียว ไม่มี state machine เต็มรูป เพราะมีสองสถานะเท่านั้น การเพิ่ม state machine เต็มรูปจะคุ้มเมื่อมีเซ็นเซอร์เข้ามาเป็นเงื่อนไข

### 4.7 ข้อมูลที่เก็บ

```text
struct Feeder {
  bool   open          ฝาเปิดอยู่หรือไม่
  unsigned long openedAt  millis() ตอนเปิดฝา
  int    countToday    จำนวนครั้งวันนี้
  int    lastDay       วันที่ของ countToday
  String lastTime      เวลาล่าสุด HH:MM
  String lastSource    แหล่งที่มา
}
```

ข้อมูลอยู่ใน RAM ทั้งหมด รีบูตแล้วหาย ข้อจำกัดนี้บันทึกไว้ในข้อ 8

## 5. ส่วนต่อประสานเว็บ

หน้าเดียว ไม่มี framework ไม่มีไฟล์ภายนอก ทุกอย่างอยู่ใน `PAGE` เพื่อให้ทำงานได้แม้ไม่มีอินเทอร์เน็ต

| องค์ประกอบ | พฤติกรรม |
|---|---|
| การ์ดสถานะ | ห้าแถว อัปเดตทุก 2 วินาทีด้วย `fetch('/status')` |
| ปุ่มให้อาหาร | `POST /feed` แล้วปิดปุ่ม 1.3 วินาที กันกดซ้ำ |
| แถบท้าย | แสดง RSSI และ IP ถ้าดึงข้อมูลไม่ได้จะขึ้นว่าขาดการเชื่อมต่อ |

การเลือกใช้ `cache: 'no-store'` กันเบราว์เซอร์มือถือคืนค่าสถานะเก่า

## 7. การรับมือความผิดพลาด

| เหตุการณ์ | พฤติกรรมปัจจุบัน | ผลต่อผู้ใช้ |
|---|---|---|
| Wi-Fi หลุด | `keepWifi()` ลองใหม่ทุก 5 วินาที | หน้าเว็บขึ้นว่าขาดการเชื่อมต่อ แล้วกลับมาเอง |
| ยังไม่ได้เวลา NTP | แสดง `--:--:--` และไม่ตั้งอาหาร | ต้องรอไม่กี่วินาทีหลังบูต |
| ฝาค้างเปิดเพราะโค้ดพลาด | ลูปปิดฝาเมื่อครบ 900 ms | ไม่มีอาหารไหลเกินหนึ่งมื้อ |
| ไฟตกตอน servo หมุน | capacitor รับกระแสกระชาก | ถ้ายังรีบูต ต้องเปลี่ยน powerbank |
| เรียกเส้นทางที่ไม่มี | 404 พร้อมข้อความไทย | ไม่มีผลข้างเคียง |
| เรียก `/feed` ด้วยวิธีอื่น | 404 เพราะลงทะเบียนเฉพาะ POST | คำสั่งไม่ทำงาน |

## 8. ข้อจำกัดที่รู้อยู่

1. ประวัติอยู่ใน RAM รีบูตแล้วหาย (FR-11 ยังไม่ทำ)
2. ไม่มีเพดานจำนวนครั้งต่อวัน (FR-08 ยังไม่ทำ)
3. ไม่มีการยืนยันตัวตน ใครอยู่ใน Wi-Fi วงเดียวกันสั่งอาหารได้
4. บัฟเฟอร์ JSON ขนาด 260 ไบต์ ถ้าข้อความแหล่งที่มาญี่ขึ้นจนล้น จะตัดค่าท้ายหายโดยไม่แจ้ง
5. ถ้า NTP sync ใหม่แล้วเวลาถอยหลังไปนาทีที่เพิ่งให้อาหารไปแล้ว ระบบอาจให้อาหารซ้ำในนาทีนั้น
6. `markFeed()` นับจำนวนครั้งก่อนที่ servo จะขยับ ถ้า servo ไฟไม่พอ การนับยังเกิดขึ้น

2. จะใช้ HC-SR04 รุ่น 5V พร้อมตัวแบ่งแรงดัน หรือรุ่นที่จ่าย 3.3V ขึ้นกับของที่ร้านมี
3. จะเก็บประวัติลง flash หรือไม่ ถ้าเวลาเหลือถึง 2 พฤศจิกายน
4. จะเพิ่ม MQTT หรือไม่ ถ้า Wi-Fi ในห้องสอบเปิดพอร์ต 1883
